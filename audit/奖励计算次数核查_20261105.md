# 奖励计算次数核查

结论：当前IsaacLab 3.0移植运行路径未发现任务奖励或AMP奖励重复累计。此前修复的是参考流重复读取时的时间推进，不是重复发奖。

实测使用真实 OnPolicyRunner.rollout_step、加载15000 checkpoint，8环境、24策略步；缩为2行地形、回合0.12秒以触发32次超时重置。没有调用optimizer或写新checkpoint。

|检查项|实测|
|---|---:|
|策略步|24|
|任务reward_manager.compute|24|
|26个非零权重奖励项|每项24|
|AMP奖励计算|24|
|收集阶段判别器forward|24|
|AMP策略关节历史append|24|
|额外观测读取|48|
|额外读取造成奖励调用/历史推进|0|
|任务奖励求和误差|0|
|PPO已存奖励对照误差|0|

每个调用是覆盖8个环境的批量调用。任务管理器使用dt=0.02，不是物理dt=0.005。奖励计算位于decimation物理循环之后，内部求解子步不重复发奖。

逐样本核验存储值：

`reward_PPO = 0.02*Σ(weight_i*term_i) + 0.25*AMP_quad + gamma*V(s_t)*timeout`

最后一项为时间上限的value bootstrap，非额外任务奖励。AMP的0.25系数按策略步加入，不再乘dt；旧PhysX环境/Instinct多奖励管理器及沿用PPO也使用这个组合方式，不是Lab3新产生的4倍/50倍重复累计。

判别器在后续优化阶段会被多次forward用于分类损失和梯度惩罚，那些调用不追加rollout奖励。本次无优化更新，因此上述forward计数仅指采样阶段。

当前日志中的episode reward由runner累计环境返回的任务奖励；PPO缓冲中还加入AMP和bootstrap。因此不能将任务日志、未乘dt的reward term和PPO存储值直接比较后判断重复发奖。

范围限制：实测针对目前配置与代码路径，不覆盖全部IsaacLab任务、录像插件或所有第三方wrapper。原训练未插入运行时计数器；奖励调用核心路径未被前一轮修复改动，源码核查也未发现原路径重复计算。reset后的AMP状态与终止前任务状态的时序属于另一项语义问题，不能与计算次数混为一谈。
